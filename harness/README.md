# 밥뭇나 Super Members

이 하네스는 **할 일을 나누고 → 담당자가 만들고 → 다른 담당자가 확인하고 → 증거를 남기는 개발 도구**입니다. 팀원이 바뀌거나 다음 날 이어서 작업해도, 무엇을 만들었고 무엇을 아직 확인하지 못했는지 알 수 있게 합니다.

## 우리 앱에 맞춘 7개 역할

아래는 사람 팀원의 별명이 아니라 **재사용하는 AI 작업 역할**입니다. 현재 모델 설정을 그대로 이어받습니다.

[일곱 토끼 캐릭터 소개판과 말 걸기](characters/README.md)에서 캡틴·케어·로직·쉴드·브릿지·프루프·키퍼를 만나보세요. 이 채팅에서도 이름과 할 일을 함께 말해 담당을 선택할 수 있습니다.

| 멤버 | 하는 일 | 제출할 결과 |
| --- | --- | --- |
| Captain · 개발 총괄 | 범위·순서·담당 파일 결정 | 작은 작업, 완료 기준, 인계 |
| Care · 사용자 경험 | 어르신 세 버튼·보호자 화면·원본 토끼 | 화면 변경과 사용성 확인 |
| Logic · 판단 규칙 | 밥솥 신호·끼니·KST 시간 규칙 | 경계값과 두 앱의 결과 비교 |
| Shield · 계정과 데이터 | 로그인·가구 분리·동의·보관 | 타인 데이터 접근 거부 증거 |
| Bridge · 스마트싱스 | OAuth·기기 선택·웹훅 | 등록·로컬 검사·실수신의 구분 |
| Proof · 독립 검증 | 구현자와 별개로 결함 확인 | 재현 방법, 검사 결과, 남은 공백 |
| Keeper · 릴리스와 복구 | 검증한 버전과 복구 절차 기록 | 변경·검증·게시 여부가 명확한 인계 |

작은 수정은 한 명이 맡습니다. 독립적인 일이 있을 때만 **총괄 + 최대 3명의 전문 역할**을 병렬로 사용합니다. `team.json`의 `owns`는 담당 후보 경로이며, 총괄이 작업마다 정확한 파일을 나눕니다. 같은 파일을 동시에 수정하지 않습니다. 검증자는 구현 파일을 고쳐서 검사를 통과시키지 않습니다.

프로젝트 역할은 `.codex/agents/`에 있습니다. 새 프로젝트 세션에서 사용할 수 있으며, 사용 중인 클라이언트가 사용자 정의 역할 선택을 제공하지 않으면 총괄이 해당 파일의 지침을 작업 메시지에 전달합니다. 파일을 만들었다고 모든 역할이 자동 실행되지는 않습니다. 구성 방식은 [OpenAI 공식 문서](https://learn.chatgpt.com/docs/agent-configuration/subagents)를 따릅니다.

## 시작하는 방법

저장소 루트에서 실행합니다. 기존 설치된 Node와 의존성을 사용하며, 이 명령들이 새 AI API나 유료 서버를 만들지는 않습니다.

```sh
# 멤버 보기
npm run harness -- team

# 로컬 실행 환경 확인
npm run harness:doctor

# 할 일·담당 역할·검사 계획 보기
npm run harness:plan -- --task harness/tasks/smartthings-pilot.json

# 변경 파일에 맞는 검사 실행
npm run harness:check

# 지정한 작업의 검사 또는 전체 검사
npm run harness:check -- --task harness/tasks/login-isolation.json
npm run harness:check -- --profile full
```

`--base <gitref>`로 비교할 기준을 지정할 수 있습니다. 작업 계획은 `smartthings-pilot`, `senior-experience`, `login-isolation` 세 개를 제공합니다. 이 계획은 실제 기능 개발을 자동 승인하는 문서가 아닙니다.

결과는 로컬 Git 제외 폴더 `.harness/runs/`의 실행별 `report.json`과 `report.md`에 남습니다. 검사 결과와 아직 필요한 수동 확인을 함께 읽습니다. 앱 화면·실기기·운영 DB의 관찰은 로컬 명령 성공만으로 채워지지 않습니다. 종료 코드 `0`은 선택한 로컬 검사 통과, `1`은 실패·잘못된 설정, `2`는 실행 준비 부족·건너뛴 검사로 인한 미완료입니다. 전체 검사에서 Firestore 검사가 건너뛰어지면 단위 검사 성공과 별개로 `incomplete`가 됩니다.

검사 전 원본·생성 파일의 일치를 먼저 확인합니다. 어긋나면 관련 빌드를 막고 올바른 원본을 수정하도록 안내합니다. 자동으로 `sync`를 실행해 누락을 감추지 않습니다. 기존 미커밋 변경은 보존하고, 검사 중 소스가 바뀌면 결과를 다시 검토하도록 표시합니다.

다음 요청부터는 이렇게 시작할 수 있습니다.

> 밥뭇나 Super Members로 [만들거나 고칠 기능]을 진행해 줘. Captain이 완료 기준과 파일 담당을 정하고 필요한 역할만 배정해 줘. 기존 무료 유지와 원본 토끼를 지키고, Proof의 독립 검증과 Keeper의 변경·검증·남은 일 기록까지 마쳐 줘.

## 개발 순서와 완료 기준

1. **요청 확인:** 최신 사용자 결정 → 제품 문서 → 현재 코드 순서로 범위를 확인합니다.
2. **계획:** 작업 계획과 변경 파일을 보고 필요한 역할·검사·수동 증거를 정합니다.
3. **구현:** 담당 파일만 수정합니다. 인터페이스가 겹치면 총괄에게 먼저 조정합니다.
4. **로컬 검증:** 해당 프로필의 검사를 실행하고 실패·건너뜀·미실행을 구분합니다.
5. **독립 검토:** Proof가 완료 기준과 실제 구현을 비교합니다. 화면 변경은 모바일·키보드·큰 글씨도 확인합니다.
6. **인계:** Keeper가 검증한 소스 버전, 남은 일과 배포 여부를 기록합니다. 필요한 경우 복구 절차를 준비합니다.

완료 단계는 **구현됨 / 로컬 검증됨 / 실제 연동 검증됨 / 배포됨**으로 나눕니다. 한 단계가 다음 단계의 성공을 뜻하지 않습니다. 작업 이후 소스가 바뀌면 이전 검사 결과를 새 버전의 증거로 쓰지 않습니다.

## 어떤 작업에 누구를 부를까?

| 작업 | 주 담당 + 검토 | 검사 프로필 | 추가로 볼 것 |
| --- | --- | --- | --- |
| 버튼·로그인 화면·토끼 | Care + Proof | `experience` | 모바일, 역할 전환, 모션 줄이기 |
| 취사·끼니·시간·알림 | Logic + Proof | `domain` | KST 경계, 오프라인, 기준 변경 근거 |
| 로그인·가구·저장 | Shield + Proof | `data` | 다른 가구 접근 거부, 동의, 로그아웃 |
| OAuth·웹훅·기기 | Bridge + Shield + Proof | `smartthings` | 실제 동의·수신·갱신은 별도 증거 |
| 하네스 자체 | Captain + Proof | `harness` | 잘못된 입력, 누락 검사, 실패 보고 |
| 여러 영역을 함께 변경 | Captain이 조정 | `full` | 각 영역의 수동 검증 공백 |

`baseline`은 공통 검사에 쓰입니다. 파일 분류는 검사를 선택하는 도구이며, 적용되는 `AGENTS.md`의 필수 검사나 완료 기준을 줄여 주지는 않습니다. 알 수 없는 경로와 패키지 변경은 `full` 검사를 선택하고 독립 검토도 거칩니다. `--profile`은 검사를 추가하며 변경 파일에 필요한 검사를 빼지는 않습니다.

## 꼭 지킬 원본과 실행 경계

- **판단 규칙:** 루트 `config/detection.ts`, `lib/judge/`, `lib/data/view.ts`가 원본입니다. `sync:firebase`가 만드는 `integrations/bapmunna-firebase/docs/shared/`는 직접 고치지 않습니다.
- **승인 디자인:** Firebase의 `docs/brand.css`와 승인된 자산이 원본입니다. `sync:design`이 `app/brand.generated.css`와 `public/brand/` 등으로 전달합니다. 처음 승인한 3D 토끼와 세 가지 어르신 행동을 보존합니다.
- **계정과 DB:** 두 앱의 기능·디자인을 맞춘다고 Supabase와 Firebase의 계정·데이터를 합치지 않습니다. 화면 역할 전환은 권한 부여가 아닙니다.
- **검사 명령:** 하네스는 계획·로컬 검사·결과 기록을 수행합니다. 결제·배포·운영 DB 변경·실기기 제어·메시지 발송은 수행하지 않습니다. 역할 지침도 그러한 권한을 새로 부여하지 않습니다.
- **비용:** 새 유료 API·인프라 의존성을 추가하지 않습니다. AI 역할을 실제 호출하는 데에는 사용 중인 계정의 이용량이 적용됩니다. 모든 역할을 매번 호출할 필요는 없습니다.

**2026-11-03 기록**에서는 삼성의 Redirect URI·웹훅 URL·읽기 권한 등록을 확인했으며, 공개 서버는 미배포이고 Target은 `PENDING`이었습니다. 이는 과거 증거이며 현재 상태를 새로 조회한 결과가 아닙니다. 현재 유지할 사용자 결정은 **Firebase Spark 무료 유지, 향후 전환 준비**입니다.

`test:smartthings`의 로컬 단위 검사와 실제 Firestore 트랜잭션 검사는 다릅니다. 로컬 emulator가 없으면 후자가 건너뛰어질 수 있습니다. 실제 OAuth·웹훅 자동 수신·토큰 갱신·2–3가구 분리도 각각 확인해야 합니다. 과거 Java 환경 문제는 `server/upgrade-readiness.md`에 기록돼 있습니다.

기존 `integrations/bapmunna-firebase/ci/`는 자동 CI의 **설치안**입니다. 실행 중인 CI나 병합 차단 장치로 표현하지 않습니다. E2E, 실사용자 사용성, RLS·실기기·푸시 검증의 남은 항목은 `todo.md`와 `test.md`에서 추적합니다.

2026-11-12 로컬 점검에서는 터미널용 `codex` 실행 파일이 누락돼 버전 명령이 실행되지 않았습니다. npm 하네스는 이 CLI와 독립적으로 동작하며, 이 작업의 전문 역할 분석·독립 검토는 현재 데스크톱의 에이전트 도구로 수행했습니다. 사용자 정의 역할의 자동 로딩을 실제 확인했다고 표시하지 않습니다.
