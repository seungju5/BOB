# CPS · 제품·기능 명세

버전: 0.3 · 작성일: 2026-10-16

파일명은 사용자 요청을 따른다. 과거 Skill의 CPS 약어 정의는 미확인이다. 여기서는 [BRD](brd.md)의 문제를 기능·입출력·인수 조건으로 연결한다.

## 핵심 흐름의 입출력

### F-01 직접 확인

- 입력: 현재 끼니와 직접 확인 의사, 선택적으로 외식 여부.
- 상태: `records[day:meal].manual=true`, 선택적 `eatOut`, `lastMealAt` 갱신.
- 출력: 해당 끼니의 직접 확인과 가족 화면 요약 갱신.
- 예외: 공유 중지, 잘못된 끼니, 아직 시작하지 않은 끼니는 기록하지 않는다.
- `lastMealAt`은 자기보고를 한 시각이다. 실제 섭취 시각이나 섭취량이 아니다.

### F-02 신호와 확인 대기

- 입력: 가상 시계, 식사 시간대·유예, 기기 신호, 연결·외출 상태, 직접 확인.
- 상태: 기기 신호는 `sensor` 요약과 기기별 활동에 반영한다. `manual`로 바꾸지 않는다.
- 출력: 직접 확인, 신호만 감지, 확인 대기, 미확인, 외출, 연결 장애 등 서로 다른 상태.
- 실제 푸시·서버 스케줄러는 없다. 브라우저를 닫은 뒤에도 전달되는 알림은 아직 제공하지 않는다.

### F-04 공유 중지

- 입력: 공유 중지 확인.
- 상태: 식사·기기 요약, 시각, 외출, 도움·관계·마음 요청, 초대와 가족 연결 등 현재 탭의 공유 데이터를 지운다. 생활·알림 설정은 유지한다.
- 출력: 공유 중지 안내. 다시 켜도 삭제한 기록을 복구하지 않는다.
- 보존하는 일별 집계와 마지막 활동 시각도 데이터다. ‘원시 이벤트 배열 없음’을 ‘아무 데이터도 유지하지 않음’으로 설명하지 않는다.

### F-06 가족 초대의 목표 흐름

보호자 초대 → 당사자·가족의 수락과 관계 확인 → 역할별 요약 조회 → 공유 중지·초대 철회. 현재 탭에서는 가상 별명·돌봄 가족/요약 보기 역할, 24시간 유효한 일회용 DEMO 코드, 수락·만료·교체·연결 해제, 역할별 요약 미리보기를 체험한다. 공유를 중지하면 초대와 가족 연결도 삭제한다. 이 가족 공유 화면은 실제 API·DB·다중 기기 동기화에 연결하지 않았다. 별도로 두 DB의 가족 스키마·서버 권한을 생성하고 검사했으며, 이것을 화면 연결 완료로 취급하지 않는다. 별도의 내 기록에서 제공하는 실제 로그인·DB 저장과 구분한다. 코드와 역할 구분은 실제 보안 수단이 아니다.

## 제품 규칙과 데모 설정

- 제품 규칙: 밥솥 개폐와 식사 직접 확인을 분리한다. WS-1·WS-2의 요구다.
- 데모 설정: 관찰 14일, 연속 미확인 2끼, 기기 신호 없음 4시간·재확인 12시간 등은 기존 프로토타입의 조절 가능한 실험값이다.
- 실제 알림 기준, AI 적용, 푸시 채널, 저장 기간, 사용자 역할은 미확정이다.
- 냉장고·전자레인지·전기포트, 관계 요청 등은 기존 데모의 탐색 확장이다. 워크시트에 없는 신규 Must로 간주하지 않는다.

검사 연결은 [test-plan.md](test-plan.md), 구현 순서는 [todo.md](todo.md)를 따른다.

## v0.2의 화면 규칙

Figma A 시작 화면·토끼, C 큰 선택 버튼, B 밥그릇을 적용했다. 소복한 밥은 직접 확인, 반 그릇은 기기 신호만, 빈 그릇은 기록 없음 또는 관찰·공유 중단을 표현한다. 실제 섭취량·영양·건강 점수로 해석하지 않는다. 직접 확인 없이 외출·오프라인·공유 중지로 바뀌면 밥그릇도 중립 상태로 바꾼다. 자세한 적용은 [design.md](design.md), 자산 출처는 [assets.md](assets.md)를 따른다.

## v0.3 계정·저장·고객관리의 인수 조건

사용자의 추가 요청으로 Firebase와 Supabase에 같은 계정 UI·데이터 구분을 추가했다. Ipilot의 공개 로그인·가입 순서를 참고했으며 내부 스키마는 복제하지 않았다.

1. 이메일/비밀번호 가입·로그인·확인·재설정을 제공하고 인증 서비스가 비밀번호를 관리한다.
2. 이메일 확인 후 저장 목적을 확인해야 실제 프로필·오늘 식사 기록을 저장한다. 가상 체험을 자동 업로드하지 않는다.
3. 같은 대한민국 날짜의 한 끼는 한 기록이다. 집/외식 종류를 갱신하고 자신의 기록을 개별 삭제할 수 있다. 최신 90개를 조회한다.
4. 소유자만 개인 기록에 접근한다. 지정된 운영자만 기본 고객정보와 내부 메모를 관리하며 개인 식사를 읽지 못한다. 클라이언트의 운영자 승격은 막는다.
5. 두 공급자의 계정과 데이터는 독립적이다. Supabase의 일반 가입 메일은 custom SMTP 설정 후 확인한다.
6. 가상 공유 중지로 서버 데이터가 삭제된다고 안내하지 않는다. 실제 가족 공유·기기·푸시와 계정 전체 삭제는 후속 범위다.

스키마·필드·권한·메일 제약은 [database.md](database.md)를 따른다.

## 간소화·전체 스키마 인수 조건

홈·기록·더보기 3개 메뉴, 두 가지 시작 선택, 한 가지 주요 제출 버튼, 목적별 설정 펼침을 적용한다. Firebase가 기본 Auth·DB이며 Supabase 계정은 별도로 유지한다. 두 백엔드에는 초대·가족 역할·생활 기준·기기 집계·알림·외출·동의 이력의 필드와 권한을 생성한다. 상세 계약과 화면 연결 상태는 database.md를 기준으로 한다.


## 관리센터 대시보드 인수 조건

관리자는 실제 조회한 회원의 가입 추이(7/30일), 운영 단계별 분포와 안내 대기를 살펴본다. 차트·수치 선택 → 회원 검색/필터/정렬 → 상세정보·단계·메모 저장으로 이어진다. 데이터가 없으면 0, 조회 실패이면 오류를 표시한다. 50명씩 추가 조회하며 부분 조회를 전체 통계처럼 표시하지 않는다. 메모 이탈 확인·실패 후 재시도·키보드 초점·320px 화면을 검증한다. 상세 UI와 조회 계약은 design.md와 database.md를 따른다.

## 사용자별 배포 연결 · 2026-10-16

F-01은 어르신용 큰 식사 버튼, F-02·03·05·06은 보호자용 요약·알림·설정·리포트·공유, F-04는 양쪽 공유 통제로 배치했다. 독립 링크로 열어도 역할별 메뉴가 유지되어야 한다. 보호자 계정에는 개인 식사 입력 폼을 표시하지 않는다. [역할별 인수 범위와 구현 상태](editions.md)를 따른다. 실제 가족 연동·푸시는 이번 분리로 완료된 기능이 아니다.
