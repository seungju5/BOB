기존 19개 검사는 익명/미확인 계정 거부, 본인 생성, 비밀번호·권한 필드 거부, 다른 UID·이메일 위장, 생성시각 변경, 자기 승격, 직원/회원의 조회 범위, 메모 검증, 오늘 식사 중복 갱신·잘못된 입력·날짜 문자열/자정 조작·삭제 권한, 기존 학사 영역 접근 거부, 대한민국 날짜, 가입·메일 확인·로그인·복구를 포함한다. 메일은 에뮬레이터에서만 발생했다.

Supabase SQL은 RLS·SQL 권한, 메타데이터를 이용한 이메일 확인 위장 차단, 본인/타인 접근, 자동 고객정보 생성, 미래 날짜·잘못된 식사 종류·운영 단계 차단, 직원의 개인 기록 접근 거부 등을 검사했다. 테스트 사용자는 Auth 목록에 남지 않음을 확인했다.

실제 UI에서 Firebase 계정의 가입 탭·필수 입력 검증·비밀번호 찾기와 CRM 로그인 차단을 확인했다. 계정 탭이 데모 전역 클릭 처리기로 초기화되는 결함을 수정하고 재검사했다. Supabase 공개 화면은 실제 provider 연결과 메일 제한 안내를 확인했다. 사용자 비밀번호 입력·이메일 수신·실제 자기보고 기록의 재접속은 사용자가 직접 수행할 첫 이용으로 남겨 둔다.

`npm run test:cloud`, `supabase/002_verify_access.sql`, `node scripts/verify-public.mjs`로 해당 범위를 재검사한다. 운영 서비스에 실제 고객을 대신해 가짜 식사·가입 기록을 넣지 않는다.

초기 v0.3 검사에서 viewport override가 선택되지 않은 탭에 적용된 시도는 모바일 통과로 취급하지 않았다. 이후 선택된 공개 앱 탭에서 실제 문서 폭을 확인해 아래 최종 검사를 수행했다. 위 초기 320/390/1280px 결과는 v0.2 체험에 대한 관찰이다.

운영자 Google 로그인 시작은 자동 승인 검토에서 차단되어 실제 운영자 세션·고객목록 UI를 통과로 기록하지 않는다. 사용자에게 본인 로그인을 요청했고 사용자가 나중에 검사하기로 했다. 서버 운영자 권한·목록·메모 접근은 에뮬레이터/SQL 검증으로 확인했다.

## 돌봄 도메인 스키마 추가 검증

Firebase 12개를 추가해 **31/31** 통과했다. 가정/동의 원자적 생성, 소유권·직원/가족 분리, 생활 기준 검증, 기기 위조 거부, 같은 배치의 개인 식사/공유 요약, 초대 일회용·역할·만료·교체, 공유 중지·재개 epoch, viewer 도움 접근 차단, caregiver 확인, 외출 범위, 불변 동의 이력, 관리 manifest 접근 차단을 포함한다.

`004_verify_care_domain.sql`의 **58개**가 실제 Supabase에서 통과했다. 14개 RLS·익명 권한, 역할 승격 거부, 초대 해시·일회용·교체·만료, 사생활 필드 제외, 기기 위조·과거/미래 관찰 거부, 연락 확인과 식사의 분리, 외출, 직원/가족 분리, 공유 중지 삭제·개인 기록 보존·재개 후 권한 미복원을 검사했다. 테스트 사용자 부재까지 확인했고 기존 데이터는 수정하지 않았다.

검사에서 새 가정 INSERT RETURNING의 조회 정책이 아직 보이지 않는 행을 helper로 조회하던 결함을 발견했다. 확인된 소유 UID를 직접 검사하도록 고친 뒤 같은 58개가 통과했다. 초대/동의 잠금 순서를 통일했고 늦은 수집이 공유 중지 후 데이터를 다시 만들지 못하도록 트리거를 추가했다.

최신 UI는 공개 배포의 HTML과 모듈이 섞이는 초기화 오류를 발견해 staging 해시와 정확한 HTML 대조, `/bapmunna`의 재검증 캐시 정책을 추가했다. 최종 브라우저·반응형 결과는 아래에 별도로 기록한다.
