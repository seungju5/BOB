# 공개 서버 배포와 팀 시연 계획

2026-11-03 기준. 삼성 OAuth **앱 등록은 완료**, 공개 서버·사용자 연결·자동 수신은 **검증 전**이다. [실제 등록 재조회](registration-status.json)와 [서버 설정](README.md)을 함께 본다.

**현재 결정:** 사용자가 “유료 전환 없이 현재 등록·구현 상태 유지”를 선택했다. Firebase Spark를 유지하며 결제 연결·유료 서비스 활성화·공개 API 배포는 진행하지 않는다. 아래 배포안과 실제 연결 시연은 보관용 계획이며, 사용자가 다시 요청하기 전 실행하거나 결제 승인을 반복 요청하지 않는다. 팀에는 구현 화면과 앱 등록 결과를 공유할 수 있고, 실제 OAuth 연결·자동 신호 수신은 미검증으로 표시한다.

## 팀원에게 한 문장으로 설명하기

“삼성에 우리 앱의 이름과 돌아올 주소를 등록했습니다. 이제 인터넷에서 작동하는 서버를 켜고, 본인 삼성 계정으로 플러그를 허용한 뒤 실제 소식이 도착하는지 확인합니다.”

```text
본인 로그인 → 삼성에서 기기 허용 → 내 플러그 선택
                                       ↓
플러그 → 삼성 SmartThings → 밥뭇나 서버 → ‘최근 신호 도착’ 화면
```

기기 신호는 실제 식사나 건강 상태의 증명이 아니다. 이번 서버는 연결 여부와 최근 도착 시각을 확인한다. 가족에게 자동 전송하거나 푸시 알림을 보내는 기능은 이 시연과 별도다.

## 보관하는 배포안

- 프로젝트 `ku-gpa`, Hosting 사이트 `impact-series`, 서비스 `bapmunna-smartthings`.
- 기존 기본 Firestore와 같은 서울 `asia-northeast3` 리전.
- 요청 기반 Cloud Run: 1 vCPU, 512 MiB, 최소 인스턴스 0, 최대 1, 요청 제한 60초. 요청이 없을 때 줄어드는 구성이다. 최대 인스턴스 설정은 청구 상한이 아니다.
- Client Secret과 암호화 키는 Secret Manager, 서비스 실행 권한은 필요한 Auth 조회·Firestore·해당 비밀만 허용한다. 비밀값은 이미지·소스·브라우저에 포함하지 않는다.
- Hosting의 `/api/smartthings/**`를 서버로 연결한다. 기존 전체 파일 지도·다른 앱 경로·설정을 보존하고 직전 버전을 복구 기준으로 남긴다.
- 운영 규칙은 현재 전체 소스에 서버 전용 collection의 브라우저 접근 금지를 병합해 검증한다. 조각 규칙으로 전체를 덮어쓰지 않는다.
- callback 쿼리에 인증 코드가 있으므로 Cloud Run 요청 로그의 해당 경로 저장을 제외하고 application 로그에는 본문·토큰·Cookie를 남기지 않는다. 기존 타 서비스의 로그 정책을 바꾸지 않는다.
- 만료 데이터는 Firestore TTL로 정리한다. TTL은 즉시 삭제가 아니며 만료·재전송 방지는 서버가 확인한다.

## 비용 결정에 필요한 내용

**현재 Spark에서 이 공개 서버를 사용하려면 Google Cloud 결제 연결이 필요하다. 연결하면 프로젝트가 Blaze 사용량 과금으로 전환된다.** [Firebase 공식 안내](https://firebase.google.com/docs/hosting/cloud-run).

| 비용 | 구조와 이번 계획 |
| --- | --- |
| Cloud Run 서버 | 실행 시간·메모리·요청 수·전송량 등에 따른 사용량 과금. 요청 기반 무료 할당량은 월 180,000 vCPU초·360,000 GiB초·200만 요청이며 결제 계정 단위 공유, 무료 크레딧 계산 기준과 리전별 가격 차이 확인 필요 |
| Firestore | 읽기·쓰기·저장·삭제 등에 따른 과금. 기본 DB의 무료 할당량은 하루 읽기 5만·쓰기 2만·삭제 2만, 저장 1 GiB. 다른 앱 사용량과 합산. **TTL 삭제는 일반 무료 삭제 할당량에 포함되지 않음** |
| Secret Manager | 비밀 버전·접근 수에 따른 과금. 결제 계정 단위 월 6개 활성 버전·1만 접근 무료 범위가 있으나 다른 서비스와 공유 |
| 빌드·이미지·로그·네트워크 | Cloud Build, Artifact Registry, 저장·전송 등의 별도 비용 가능. 배포 빈도와 실제 사용량으로 확인 |
| 삼성 SmartThings | Google 비용과 별개. 팀의 이용 형태·국가·계약 조건 확인 필요. 앱 등록 성공은 영구 무료나 Business 이용 계약 성립을 뜻하지 않음 |

근거: [Cloud Run](https://cloud.google.com/run/pricing), [Firestore](https://cloud.google.com/firestore/pricing), [Secret Manager](https://cloud.google.com/secret-manager/pricing), [삼성 10월 30일 공지](https://blog.smartthings.com/smartthings-updates/smartthings-api-additional-details-for-developers-and-business-partners/). 무료 범위가 있어도 월 청구액 0원을 보장하지 않는다. 실제 서울 리전 단가·세금·환율·공유 사용량과 삼성 요금이 정해지기 전 전체 월 정액을 확정하지 않는다.

### 가구가 늘어나면 무엇이 늘어나는가

계산 예시일 뿐 실측값이 아니다. 가구마다 플러그 1개, 관련 이벤트가 1분에 1개씩 별도 요청으로 도착하고 30일 동안 지속된다고 가정한다. 이벤트 구독 방식이므로 앱이 1분마다 삼성 API를 호출하도록 설정한 것은 아니다.

| 가구 | 월 이벤트 | 하루 DB 읽기 약 3회/이벤트 | 하루 DB 쓰기 최대 2회/이벤트 | 만료 후 월 TTL 삭제 약 |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 43,200 | 4,320 | 2,880 | 43,200 |
| 2 | 86,400 | 8,640 | 5,760 | 86,400 |
| 3 | 129,600 | 12,960 | 8,640 | 129,600 |
| 1가구 추가 | +43,200 | +4,320 | +2,880 | +43,200 |

읽기는 installation 조회와 트랜잭션의 connection·receipt 조회를 합쳤다. 쓰기는 중복 방지 메타데이터와 도착 시각 갱신이다. 재시도·트랜잭션 재실행·로그인·수동 확인·토큰 갱신·관련 없는 기기 이벤트·기타 앱 사용량은 별도로 더해진다. 기기 전송 빈도가 다르면 사용량도 달라진다. 이 표의 이벤트 수를 삼성의 청구 API 호출 수와 동일하게 간주하지 않는다.

2–3가구 파일럿은 서버 하나를 공유하므로 가구마다 서버 정액 요금이 새로 붙는 구조가 아니다. 이벤트·저장·삼성 사용량과 추가 플러그 구입비가 늘어난다. 배포 첫날 실제 이벤트 수·실행 시간·청구 지표를 보고 다시 계산한다.

제안: 프로젝트 범위 월 1만 원 예산 **알림**을 설정하고 50%·90%·100% 도달을 확인한다. 이는 자동 중단이나 요금 상한이 아니다. 사용자의 결제 연결 결정 전 유료 서비스는 활성화하지 않는다.

## 실제 성공을 확인하는 순서

1. 공개 `/api/smartthings/config`가 `enabled:true`를 반환하고 본문·로그·프런트 파일에 비밀값이 없는지 확인한다.
2. `apps:register`로 삼성의 Target 확인을 요청하고 앱을 재조회해 `CONFIRMED`를 확인한다. 서명 검증을 끄거나 임의 성공 응답으로 대체하지 않는다.
3. 밥뭇나에서 **본인 Firebase 로그인 → 삼성 동의 → 본인 전력 측정 플러그 선택**을 직접 진행한다. OAuth 토큰이 브라우저에 노출되지 않는지 확인한다.
4. 실제 플러그를 평소처럼 사용한 뒤 **삼성 webhook으로 받은 새 도착 시각**을 화면과 서버 메타데이터에서 대조한다. ‘지금 확인’의 수동 조회와 자동 webhook을 구분한다. 신호가 오지 않으면 대기·원인을 그대로 표시한다.
5. 새로고침·재로그인, 연결 해제·재연결, 다른 계정에서 정보가 보이지 않는지 확인한다. 24시간 이후 토큰 갱신은 실제 시간이 지난 뒤 별도 검증한다.
6. 2–3가구는 각 계정 소유자의 동의로 같은 순서를 반복한다. 한 계정에서 성공한 것을 모든 가구 검증으로 확대하지 않는다.

## 팀 공유용 2분 시연

| 시간 | 화면·행동 | 설명 |
| --- | --- | --- |
| 0:00–0:20 | 토끼 로그인 화면 | “기존 토끼를 그대로 사용하고, 본인 계정으로 시작해요.” |
| 0:20–0:50 | 삼성 동의 후 플러그 선택 | “삼성이 허락한 내 기기 중 하나를 골라요.” |
| 0:50–1:20 | 연결됨과 실제 신호 도착 시각 | “플러그 소식이 우리 앱까지 왔어요.” 실제 수신했을 때만 사용 |
| 1:20–1:40 | 수동 확인·연결 해제 안내 | “연결 상태를 확인하고 원하면 끊을 수 있어요.” |
| 1:40–2:00 | 완료 범위와 다음 단계 한 장 | “현재는 기기 연결 검증, 식사 판정·가족 알림은 다음 검증이에요.” |

공유 자료에는 개인 이메일·전화·기기 ID·토큰을 넣지 않는다. 화면 캡처는 팀 공유에 필요한 부분만 남긴다. 실제 성공 후 캡처·짧은 시연·완료 범위 요약을 추가하고, 그 전에는 완료 보고서로 배포하지 않는다.
